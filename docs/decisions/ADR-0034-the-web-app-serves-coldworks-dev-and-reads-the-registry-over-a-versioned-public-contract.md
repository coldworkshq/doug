> **Proposed, not accepted.** The founder's flip of this record to `accepted`
> is the signature on the read contract (hq#16, 2026-09-10). Until then the
> registry does not deploy the route this record reads, and nothing in this
> repo renders a figure from it. Number claimed on #323.

## Context

Two origins serve one product today. `doug.coldworks.dev` is this app: the
landing, the docs, the public queue and scoreboard, and behind WorkOS
sign-in, a dashboard keyed on the GitHub organization. `coldworks.dev` is a
second Next.js app in the `coldworkshq/coldworks` repo: the Coldworks landing
page, the audit CLI's docs, and six read-only engine screens over a pushed
mirror of the registry, with its own WorkOS application. A visitor who
installs Doug from the Coldworks landing comes back to a different site with
a different session and a rail that has no Overview, no Memory, and no
Guards. The founder ruled on 2026-09-10 that this is two products wearing one
logo, and that the product is one: one origin, one session, one rail
(Overview, Reviews, Memory, Guards), one web app.

The direction of dependency decides which app. Doug is the product and
Coldworks is the engine, so the product reads the engine and the engine
never reads the product. Today the engine repo hosts the front door, which
is backwards. This app already has the tenant model, the sign-in, the install
flow, the ledger, and settings; the registry app has a data layer and six
screens over one tenant of synthetic wind-tunnel data. So the shell is this
app, and the registry becomes something it reads.

`web/lib/links.ts` has said since 2026-08-20 that nothing in `web/` imports
from Coldworks. That was written to keep Doug shippable on its own, and it
still is: a runtime fetch of a public JSON document is not an import, and
Doug renders a chip with a reason when the document is missing.

## Decision

1. **This app serves `coldworks.dev`.** The apex is mapped onto `doug-web` as
   a second domain mapping; `doug.coldworks.dev` keeps its mapping and
   answers every request with a path-preserving permanent redirect to the
   apex, so links already written into pull requests keep working. Sign-in
   stays on exactly one host: `auth-origin.ts` keeps its single configured
   host, which becomes the apex. The redirect URI rotates and the image is
   rebuilt through `api/deploy/domains.sh cutover`'s existing sequence (map,
   verify the certificate, rotate the secret, rebuild, flip `DOUG_WEB_URL`);
   the registry's own apex mapping is removed last.

2. **This app reads the registry over a versioned public JSON contract.**
   `GET /api/registry/v1/snapshot` on the registry service serves the seven
   row sets its screens render plus three centralized counts, in an envelope
   with `schema_version`, `tenant_id`, `generated_at`, `served_at`, `stale`,
   `stale_after_seconds`, `reason`, `provenance`, and `synthetic`, none
   optional. A refusal is the same document with `snapshot: null` and a
   `reason`, at 503. The schema and a fixture are generated by the registry
   and carried here as byte copies under `web/lib/registry-contract/`,
   pinned by SHA-256 in `web/lib/registry-shape.ts`:

   - schema `a41e9d6642cd197017c34a8de8d4fe381727b065cec94816fa1957ae04b649ec`
   - fixture `d4587bb825dea93c4006a9473274199b9d30959868a57578f1e61925aa071a10`

   `registry-shape.ts` is this app's own description of the shape, tested
   against the schema key for key and null for null. `registry-api.ts` is
   the only reader. It returns a snapshot or `unknown` with a reason, and
   never a bundled fallback: any failure, any non-200, any body the guard
   rejects, a schema version this build does not know, a document that says
   it is stale, or one older than its own window when read, is `unknown`.
   A page renders exactly one of two things from it: a figure beside the
   sentence the document carried for it, or a chip with the reason.

3. **The contract is public read, with no credential.** The same data is
   public on six signed-out screens today; API keys beyond the seeded dev
   key stay banned in the engine repo; and a cross-project IAM read has no
   precedent in either deploy script. The reader carries an unused bearer
   slot (`COLDWORKS_REGISTRY_BEARER`) so that when a per-tenant figure
   exists and the route moves behind IAM, the change is an environment
   variable.

4. **Who may see the registry is a mapping the founder sets.**
   `DOUG_GUARDS_INSTALLATIONS` maps an installation id to an engine tenant,
   in the shape of `DOUG_INTENT_INSTALLATIONS`: unset maps nobody, a
   malformed entry refuses loudly. An unmapped installation renders the
   chip on the same code path a mapped one renders the figure on.

5. **The review lane is untouched, and a CI job proves it.** Any pull
   request from a `shell/` branch fails if its diff names
   `api/doug/review.py`, `api/doug/worker.py`, or `api/doug/check_run.py`, or
   if any hunk of `api/doug/api.py` overlaps the GitHub webhook handler.
   The job was shown red once, on a probe branch, before this record was
   opened for signature.

## Rejected

- **A redirect from the Coldworks landing to this dashboard on its own
  host.** Ruled first, on 2026-09-10, and amended the same day: a login that
  lands on a second origin with a second look is two products.
- **The registry app absorbing this dashboard.** It moves this app's web
  across the repo boundary on cadence and dependency direction, makes the
  engine's web app a client of doug-api, and the registry has no tenancy in
  its web layer.
- **Two apps cross-linked with one identity.** Cheap and honest, but the
  landing's "one workspace" sentence would be false.
- **A shared database read of the mirror.** A live credential to another
  project's Postgres, covered by no ruling.
- **An API key on the route.** Banned in the engine repo.
- **Cloud Run IAM in the first version.** No precedent in either deploy
  script and no need while the data is public; it arrives with the
  per-tenant figure.
- **An allowed-host set for sign-in.** Two sign-in origins is what the
  registry's own sign-in ruling reasoned against on 2026-09-09; the subdomain
  redirects instead.
- **Moving `doug-web` into the engine's GCP project, or a load balancer
  presenting one origin.** The first moves the protected side; the second
  is infrastructure whose only job is to fake one origin.
- **A bundled fixture fallback in the reader.** A figure with no sentence,
  which is the one thing the contract exists to prevent.

## Consequences

- `links.ts` is amended: the runtime fetch is named as the one runtime
  dependency on Coldworks, and the apex note is retired because the apex is
  live.
- The cutover is the one production-facing step, and it is reversible
  because no mapping is deleted before its replacement is verified. The
  redirect URI is inlined at build time, so there is no environment flip
  for it; `domains.sh cutover` rebuilds.
- `api/deploy/gcp.sh` refuses every deploy once `doug-web` holds two
  mappings unless `DOUG_WEB_DOMAIN` is set, so `deploy.yml` sets it to the
  apex before the second mapping is created.
- A snapshot older than its window, or one the registry declares stale, is
  never a number on a page. The chip says why, in the registry's own words
  where it gave them.
- The registry stops being a customer surface: its sign-in, landing, and
  docs leave it in a later change in the engine repo, and its screens stay
  reachable on its own host as the engine's instrument until this app
  absorbs them one at a time.
- ADR-0006's rule that Doug does not depend on lema is not reopened. This
  record adds one runtime read of the engine's registry and nothing of
  lema's; the amendment is to the sentence in `links.ts`, recorded here so
  the reader sees it as a decision and not a drift.
